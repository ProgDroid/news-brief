**2026-06-24 — SPEC + PLAN WRITTEN & COMMITTED, implementation NOT yet started.** Came out of `docs/2026-06-24-audit-todo.md` item #1 ("topic-novelty filter"), but investigation **overturned that premise**: (1) "Chroma" in this project is a remote *podcast-archive* MCP, not an embedding store of the brief's own content — there is NO embedding substrate for the brief; (2) classifying 7 real consecutive briefs (18-24 Jun) showed the repetition is **claim-level** (durable facts/frames re-stated near-verbatim daily — BOJ-hike, "China may miss 4.5-5%", BCA 60%, $90-100 floor — inside topics that are *correctly* covered daily), NOT topics resurfacing. So a topic suppressor (chubbot's design) would do nothing or harm. **Smoking gun:** `yesterday_block` fed `yesterday_brief[:2000]` (~TOP STORIES only) → the model was blind to the back-half sections (Japan/China/Iran-pulse) where the worst repetition lives.

**Design = two parts** (`docs/superpowers/specs/2026-06-24-brief-claim-memory-design.md`, commit 45ebfdc): **(A)** feed yesterday's brief whole (`[:2000]`→`[:6000]`) + strengthen the "no significant change" instruction to cover standing frames; **(B)** a model-maintained **standing-claim ledger** (`brief_memory.json` on the deploy volume) injected as an `ESTABLISHED` prompt block and reconciled by a SEPARATE small post-gen Claude call (Haiku 4.5, raw HTTP like submit_batch). Decisions: model returns the full updated ledger (code stamps dates/ids — deterministic by `id`, no fuzzy matching); reconcile is its own call NOT a second `@@@` block (dodges the [[signals-delimiter-fragility]] + [[signals-parse-error-is-truncation]] pains); decay = self-expiry (retire claims not reaffirmed in 7 days — accumulated memory, no hard window). Fail-safe everywhere (any error → prior ledger kept, brief unaffected). Flag-gated `BRIEF_MEMORY_ENABLED` (default OFF; Part A ships unconditional).

**2026-06-25 REGRESSION FOUND + FIXED (commit 51b39c6, TDD, 367 tests).** First live-ish run logged `reconcile failed; keeping prior ledger: no JSON array in reconcile response: '```json\n[...'`. Root cause = TRUNCATION, not a parse bug: reconcile re-emits the whole ledger as a JSON array but `_messages_call` capped output at `max_tokens=2048`; a full ~25-claim ledger (or a rich first-run brief with no output bound) overran it → array cut off before closing `]` → `re.search(r"\[.*\]")` found no match → generic "no JSON array" → fail-safe kept prior ledger EVERY run = silent no-op of the whole feature. The ` ```json ` fence is NOT the bug (regex looks inside it fine); the 200-char log preview (`text[:200]`) also misleadingly looked like the cutoff. Fix = (1) `RECONCILE_MAX_TOKENS=4096`, (2) prompt now bounds output to "at most {MAX_CLAIMS} terse claims", (3) `_messages_call` checks `stop_reason=="max_tokens"` and raises a clearly-attributed truncation error so it never masquerades as a parse failure again.
