When `split_brief_and_signals` returns `status="parse_error"` (marker present, no parseable trailing JSON array), the root cause is almost always **output truncation**, not a parser/delimiter bug. The batch hit `stop_reason="max_tokens"`, cutting the `@@@SIGNALS@@@` array off mid-object so there's no closing `]` to recover.

Key trap: with web search enabled (`submit_batch` adds `web_search_20250305`), `max_tokens` is a **whole-turn budget** — interleaved reasoning `text` blocks + `server_tool_use` query blocks across many agentic turns all count, so the budget drains long before the final signals array. On 2026-06-01 a run had 60 text blocks + 6 searches and truncated at MAX_TOKENS=4096; bumped to 16384 (commit bd9e052). Sonnet 4.6 ceiling is 64k output / 90k OTPM, so there's plenty of headroom if it recurs.

**How to apply:** First check `stop_reason` in the logs, not the parser. `fetch_batch_results` → `_dump_raw_batch_result` logs a one-line summary every run and writes the full payload to `/app/logs/debug/batch-raw-*.json` only on anomalies (`stop_reason != end_turn` or empty text). If truncated again, raise MAX_TOKENS or trim the prompt. Distinct from [[signals-delimiter-fragility]] (that's the model mangling the marker; this is the array never finishing).

**RECURRENCE #4 (2026-07-02) — a NEW trigger: the Sonnet 5 tokenizer, not thinking.** On the 2026-07-02 collect the forced-tool signals call failed with `emit_signals input missing 'signals' list` (the tool block WAS present — so the JSON was cut off mid-array, not absent). No `Signals API attempt N failed` line preceded it → the API call SUCCEEDED; the truncation was `max_tokens`, not transport. Cause: `claude-sonnet-5`'s tokenizer emits ~30% more tokens for the SAME content, so the signal-rich brief's `emit_signals` output overran the `max_tokens=2048` that fit fine under Sonnet 4.6 — **even though thinking is disabled on that call** (so this is the tokenizer mechanism, DISTINCT from the adaptive-thinking one in [[newsbrief-model-config]]). Fix dfabcd1: `SIGNALS_MAX_TOKENS 2048→8192` + `extract_signals` now logs `stop_reason`+`usage` BEFORE parsing (the fail-safe used to swallow the one datum — `stop_reason=max_tokens` — that identifies truncation; the "CAPTURE stop_reason" advice below is now built into the code). Diagnostic signature to reuse: the two log lines partition the cause — `Signals API attempt N failed:` = transport/HTTP; a bare `missing 'signals' list` with NO attempt line = max_tokens truncation.

**GENERALIZE — this is a project-wide rule, not signals-only (the `@@@SIGNALS@@@` + `split_brief_and_signals` mechanism above is now REMOVED; signals moved to forced-tool extraction, see [[signals-extraction-separate-call-followup]]).** The SAME bug recurred 2026-06-25 in a totally different post-gen call: `brief_memory.reconcile_ledger`'s Haiku call capped output at `max_tokens=2048`, the model re-emits the whole standing-claim ledger as a JSON array, it overran and was cut off before the closing `]`, and the regex parser misreported it as "no JSON array" → fail-safe silently no-opped the feature every run (fixed 51b39c6: budget→4096, prompt bounded to ≤MAX_CLAIMS terse claims, `_messages_call` now raises on `stop_reason=="max_tokens"`). RULE for EVERY separate post-gen Claude call (reconcile, dig, weekly-summary, any future one): size BOTH `max_tokens` AND `timeout` to the call's real workload, CAPTURE `stop_reason` so a cutoff surfaces as truncation not a parse/format bug, and treat any "couldn't parse the model's structured output" as truncation-until-proven-otherwise. Timeout sibling of this rule: [[signals-extraction-separate-call-followup]] (a post-gen call's timeout must match its model's latency).
