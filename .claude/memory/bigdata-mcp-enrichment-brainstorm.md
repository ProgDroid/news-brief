**OAuth DISCOVERY FACTS (fetched 2026-06-24 from well-known metadata):** MCP server `https://mcp.bigdata.com/` (Streamable HTTP), required scope `openid`, bearer in header. Auth server = **Clerk**: issuer `https://clerk.bigdata.com`, authorize `…/oauth/authorize`, token `…/oauth/token`, revoke `…/oauth/token/revoke`. **`grant_types_supported` INCLUDES `refresh_token`** ✓; PKCE `S256` required; `token_endpoint_auth_methods` = `none`/`client_secret_basic`/`client_secret_post` (→ public-client + PKCE refresh works WITHOUT a client secret — the clean self-managed-refresh shape). TWO YELLOW FLAGS to confirm live: (1) **`offline_access` NOT in scopes_supported** — refresh grant exists but whether a `refresh_token` is actually ISSUED depends on Clerk app config + scope; only the live token response confirms (bigdata markets "automatic renewal" + Claude.ai stays connected for days → likely YES). (2) **NO `registration_endpoint`** advertised → Dynamic Client Registration may be unavailable; a direct client may need a pre-provisioned `client_id` created in the bigdata/Clerk account.

**PIVOT 2026-06-24 — OAuth path abandoned for API-KEY path (much simpler).** MCP Inspector OAuth flow FAILED: `Incompatible auth server: does not support dynamic client registration` (the no-DCR yellow flag materialised — Clerk DCR is off, headless OAuth would need a pre-provisioned client_id the user can't self-make). BUT bigdata docs (`docs.bigdata.com/mcp-reference/api-integrations/mcp-api-integration`) show the Remote MCP **also accepts a static API key** — header **`x-api-key`** (NOT Bearer), `type:http`, url `https://mcp.bigdata.com/`. mcp.json: `{"mcpServers":{"mcp.bigdata.com":{"type":"http","url":"https://mcp.bigdata.com/","headers":{"x-api-key":"${KEY}"}}}}`. Keys from the **Developer Platform `https://platform.bigdata.com/api-keys`**. This KILLS the whole token-refresh design fork (API keys are long-lived → genuinely one-and-done; no Clerk, no DCR, no refresh loop) and strongly favours **Fork B** (direct MCP client setting `x-api-key`; note Fork A / Anthropic `mcp_servers` connector sends `authorization_token` as Bearer, not `x-api-key`, so Fork A may not fit bigdata's API-key auth).

**RESOLVED 2026-06-24 — DEAD-END for self-serve: bigdata headless hits the SAME business-email gate as REST.** User checked `platform.bigdata.com/api-keys` → it redirects to the **business-email REST-API access** sign-up (their personal/trial account can't generate a key). User also tried scraping a `client_id` from platform.bigdata.com network requests into MCP Inspector → FAILED (that's the platform SPA's Clerk *publishable/frontend* key, not an OAuth client_id; wrong type + localhost redirect not whitelisted). CONCLUSION: bigdata's only OAuth integrations are the 3 partner connectors (Claude/ChatGPT/Copilot — pre-registered clients, interactive only, NOT reusable headlessly); every self-owned automated door (REST key, `x-api-key` MCP, custom OAuth client) routes through the gated business-email developer approval. The MCP that works in Claude TODAY does so only via Anthropic's partner client + interactive login — that does NOT transfer to a headless client. **So the MCP idea does NOT remove the REST barrier.** Silver lining: the one business-email key unlocks BOTH REST and x-api-key MCP, and x-api-key MCP is then the BETTER build than REST (live tool shapes already captured → no "unverified field names" risk). Gate is beatable via custom-domain email (Cloudflare Email Routing + Zoho ~£10/yr, see [[bigdata-evaluation-and-trading-split]]) — friction, not a contract.

**ToS CONSTRAINT (reviewed 2026-06-24, bigdata.com/terms-and-conditions):** Individual use is EXPLICITLY allowed (Customer = "any individual or entity"; §3.1 "Individual Users"; no truthful-registration clause; authority-to-bind applies only to §3.2 Business Customers) → registering as an individual on an owned domain (`bigdata@aegypt.fyi` via Cloudflare Email Routing) is contract-clean; the business-email gate is form friction only. BUT the terms PROHIBIT "copy, store, archive, cache, or create a database of the Bigdata Content." Consequences: (a) the deferred bigdata enrichment must NOT persist raw bigdata content snapshots — the shipped `enrichment-<date>.json` snapshot path must store only derived/non-content fields (or use transiently) when on the bigdata provider; (b) a bigdata-sentiment HISTORICAL backtest is effectively ToS-barred ("create a database of their content") — independently confirms AV (not bigdata) is the backtest source. NY governing law; liability capped at trailing-12mo fees; standard indemnity (low risk at small spend). The current AV backtest uses ZERO bigdata content → unaffected.
