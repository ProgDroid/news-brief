**Raised 2026-06-24 during the claim-memory brainstorm ([[brief-claim-memory-build]]); DECIDED + BUILT 2026-06-25.** The first `@@@SIGNALS@@@` block shared the brief's token budget and a literal text marker, so it hit the same two pains as the (avoided) reconcile-tail: [[signals-delimiter-fragility]] (marker mangled) and [[signals-parse-error-is-truncation]] (max_tokens cut the array). Fix = extract signals in a SEPARATE post-gen call reading the FINISHED brief, same shape as `brief_memory.reconcile_ledger`.

**Decisions (locked with the user):** (1) **forced tool-use** — a single `emit_signals` tool with enum-constrained direction/confidence/asset_class and nullable ticker/thesis_ref/provenance (non-required); schema-guaranteed JSON, no marker to mangle, no shared budget to truncate. (2) **Sonnet 4.6** (`claude-sonnet-4-6`) for the extractor (judges position-relevance/direction → feeds paper trading); reconcile stays Haiku. (3) **Two separate calls** (signals + reconcile both read the finished brief but stay independent, single-responsibility, ~$0.002/day). (4) Schema field-set UNCHANGED (paper-tracker consumer contract); only the JSON-schema tightening (enums + required/nullable) is new. Accepted tradeoff: provenance fidelity drops slightly (extractor reads finished prose, not generation-time source knowledge) — user OK with it.

**REGRESSION FOUND + FIXED 2026-06-25 (commit e255436):** the new `_post_messages` inherited `timeout=30` from the Haiku reconcile call, but `extract_signals` uses Sonnet 4.6 — its synchronous tool-use generation tips past 30s → `Read timed out` → fail-safe `extract_error` → the day's signals snapshot overwritten with `[]` (`status=extract_error`). Wiped ALL paper trading (equity/crypto/prediction read the same `signals-<date>.json`). The unit tests missed it because they stub the `call` seam, so the real timeout was never exercised. Fix: `SIGNALS_TIMEOUT=90` + one retry (`SIGNALS_MAX_ATTEMPTS=2`); safe because extraction runs AFTER delivery so latency is free. **LESSON: a synchronous post-gen call's timeout must match its MODEL's latency, not be copied from a faster model's call.** NOTE: the deploy host re-runs the whole pipeline on every image pull, so a failing post-gen call corrupts state on every redeploy, not just at the cron.
