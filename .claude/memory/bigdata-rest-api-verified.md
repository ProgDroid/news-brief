**COST FINDING (brainstorm input):** search is ~**528 units/call** vs 50 for sentiment/events, 1 for resolve. `bigdata_help` reported `payg.balance: 1000` — if that balance is denominated in these same units it is TINY (≈2 searches); more likely 1000 is credits/$ that these tokens draw down via a price table (topup at app.bigdata.com/billing). **Must pin the unit↔balance↔$ meaning + set daily fan-out ceilings before enabling** — current defaults `ENRICHMENT_MAX_SYMBOLS=20` / `MAX_THEMES=8` (8 theme searches ≈ 4200 units/day + 20 sentiment+events ≈ 2000) could be pricey. This is the old "cost lever = fan-out" note made concrete.

Other REST endpoints for later depth: `analyst-estimates` (estimates + earnings-surprises), `search-volume` (sentiment aggregated by date), `co-mentions/connected-entities|topics`, `knowledge-graph/autosuggest`. OpenAPI: `docs.bigdata.com/api-rest/openapi/openapi.json`.

**THE MODEL-RESHAPE DECISION (the one real design fork):** `SentimentScore(current, baseline, zscore_1mo, zscore_1qt, regime, confidence)` in `models.py` was modeled on the MCP tearsheet markdown, which does NOT exist as REST JSON. Real REST gives `daily_sentiment` + `sentiment_pressure` + `abnormal_media_attention` time series. Two options: (a) compute baseline/z/regime ourselves from the series (re-derives what the vendor already normalized; more code + tests), or (b) **reshape `SentimentScore` to the vendor's native fields** (latest `daily_sentiment`, `sentiment_pressure`, `abnormal_media_attention`) — cleaner, honest, less code. RECOMMEND (b). This ripples into `render.py` (`render_prompt_block`), `annotate_signals`, and their tests. NOTE the MCP `bigdata_sentiment_tearsheet` tool returns a MARKDOWN narrative (not JSON) — matches the earlier probe finding that numeric tearsheet ≠ retrievable JSON.
