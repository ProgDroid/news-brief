# Signals extraction as a separate post-gen call — design

**Date:** 2026-06-25
**Status:** Approved, ready for implementation plan
**Origin:** Follow-up raised 2026-06-24 during the claim-memory brainstorm. The
standing-claim ledger deliberately reconciled via a separate post-gen call to
dodge two documented brief-tail pains; this applies the same move to the
`@@@SIGNALS@@@` JSON extraction, which suffers the identical pains.

## Problem

The daily brief is generated by a single Batch API call (`submit_batch`, web
search on). The model returns prose **and** a trailing `@@@SIGNALS@@@` delimiter
+ JSON array of position signals in one response. Collect-time code
(`split_brief_and_signals`) separates the two.

This single-response design causes two recurring failures:

1. **Delimiter fragility** — the model restyles or drops the literal
   `@@@SIGNALS@@@` marker (notably collapsing it to a bare `---`). The parser
   carries three fallback layers and a legacy `---SIGNALS---` marker purely to
   recover from this.
2. **Truncation cuts the array** — signals share the brief's `max_tokens`
   budget. When prose runs long, the JSON array is cut off mid-structure,
   yielding `status="parse_error"` and lost signals.

Both are structural consequences of co-generating machine-readable JSON with
free prose under one token budget and one literal text marker.

## Goal

Move machine-readable signal extraction out of brief generation into a separate,
schema-enforced post-gen call that reads the **finished** brief — eliminating
both failure modes at the root, and reusing the proven separate-call pattern
already shipped for the claim-memory ledger (`brief_memory.reconcile_ledger`).

Non-goal: changing the human-readable `📌 POSITION SIGNALS` prose section, the
signal schema, the paper-tracker consumer contract, or the persisted
`signals-<date>.json` shape.

## Decisions

- **Schema enforcement: forced tool-use.** The extractor call defines a single
  tool `emit_signals` whose `input_schema` is the 7-field signal schema (enums
  for `direction`/`confidence`/`asset_class`) and forces it via `tool_choice`.
  The model cannot emit a stray marker or truncate the array — structured output
  is guaranteed. This kills both pains at the root.
- **Model: Sonnet 4.6** (`claude-sonnet-4-6`). Judging position-relevance,
  direction, and confidence feeds (paper) trading, so stronger reasoning is
  worth the negligible cost over Haiku. (Reconcile stays on Haiku.)
- **Topology: two separate calls.** Signals extraction and ledger reconcile both
  read the finished brief but remain independent calls — single responsibility,
  independent fail-safe, smaller responses each (no truncation creep). ~$0.002/day
  combined.
- **Location: extend `brief.py`**, not a new module. Keeps all signals logic
  (extract / normalize / save) in one tested home and avoids the
  Dockerfile-COPY / CI-paths triple-update a new top-level module requires.

## Design

### 1. Brief prompt — remove the JSON tail, keep the prose

Strip the `@@@SIGNALS@@@` delimiter instruction and the JSON schema block from
`DAILY_SYSTEM_PROMPT` (currently `brief.py:1567-1585`). The `📌 POSITION SIGNALS`
prose section (`brief.py:1560`) stays — it is the human-readable surface. The
brief call now produces prose only and spends its full `max_tokens` on prose.

### 2. New extractor — `extract_signals(brief_text, *, call=None) -> tuple[list, str]`

Added to `brief.py` near the existing signals functions. Behavior:

- Builds a Sonnet 4.6 messages call with a single tool `emit_signals`:
  `input_schema` = `{type: object, properties: {signals: {type: array, items:
  <7-field schema with enums>}}, required: [signals]}`, and
  `tool_choice = {type: "tool", name: "emit_signals"}`.
- Prompt instructs the model to read the **whole** finished brief (so it also
  captures `📊 MACRO SIGNAL` items, not just the position section), and to derive
  `provenance` from sources the brief cites where present, else `null`.
- Parses the response by locating the `tool_use` block and reading
  `.input.signals`.
- Returns `(raw_signals, status)` where `status ∈ {"ok", "extract_error"}`.
- Fail-safe like `reconcile_ledger`: any exception (HTTP, parse, missing tool
  block) → `([], "extract_error")`, logged at warning; the brief is unaffected.

A `call=None` injection seam (defaulting to a raw-HTTP helper using
`ANTHROPIC_HEADERS`) makes the function unit-testable with a stub, mirroring
`reconcile_ledger(..., call=None)`.

### 3. Delete the dead parsing layer

Remove `split_brief_and_signals`, `_find_trailing_json_array`, and
`_SIGNAL_MARKERS` (`brief.py:1628-1690`). Their only purpose is recovering the
inline marker/array format, which no longer exists. Net code reduction.

### 4. Keep `normalize_signals` + `save_signals` unchanged

`normalize_signals` stays as defense-in-depth (synonym coercion, `asset_class`
default) even though tool-use enums make most coercion redundant. `save_signals`
already records `status` and `dropped`, so `extract_error` flows through to the
dated snapshot. A quiet day (`status="ok"`, empty array) stays distinguishable
from a failed extraction (`status="extract_error"`, empty array).

### 5. Call-site reorder (both `mode_collect` and `mode_run`)

```
raw = poll_batch(...)
brief = raw.strip()                          # raw IS prose now
deliver(brief, ...)                          # deliver first — extraction never delays the brief
raw_signals, status = extract_signals(brief)
signals, dropped = normalize_signals(raw_signals)
save_signals(signals, today, status=status, dropped=dropped)
if brief_memory_enabled():                   # unchanged, runs after
    save_ledger(reconcile_ledger(load_ledger(), brief, today))
```

Delivering before extraction means a slow or failed Sonnet call never holds up
the user's brief — the same posture as the reconcile call today.

## Data flow

```
Batch API (brief, web search)  ──>  prose brief
                                      │
                                      ├─> deliver() ──> Telegram + archive
                                      │
                                      ├─> extract_signals()  [Sonnet 4.6, forced tool-use]
                                      │     └─> normalize_signals() ──> save_signals() ──> signals-<date>.json
                                      │
                                      └─> reconcile_ledger()  [Haiku 4.5, if enabled] ──> brief_memory.json
```

## Error handling

- **Extraction call fails** (HTTP error, timeout, no `tool_use` block, malformed
  input): `extract_signals` returns `([], "extract_error")`. `save_signals`
  persists an empty dated snapshot with `status="extract_error"`. The brief is
  already delivered and unaffected.
- **Empty signals (legitimate quiet day):** `([], "ok")` — persisted with
  `status="ok"`, distinct from the failure case.
- **No inline fallback exists anymore.** The extractor is the sole path to
  signals; this is intentional and strictly better than silent truncation, but
  means the separate call is load-bearing.

## Testing (TDD)

`tests/test_signals.py`:

- `extract_signals` with an injected `call` stub returning a `tool_use` block →
  asserts parsed signals match.
- Fail-safe path: stub raises → asserts `([], "extract_error")`.
- Missing/empty `tool_use` block → asserts `([], "extract_error")`.
- Confirm `normalize_signals` still coerces/normalizes extractor output.
- Remove the now-dead `split_brief_and_signals` / `_find_trailing_json_array`
  tests.

CI runs on the full checkout (`requirements.txt` + dev), no pandas needed here.

## Tradeoffs accepted

- **Provenance fidelity drops slightly.** The generating model knew which feed a
  signal came from; an extractor reading finished prose only knows what the prose
  cites, so `provenance` will more often be `null`/coarse. It was always
  best-effort.
- **One extra synchronous call at collect time** (~$0.002/day). Collect already
  makes the reconcile call synchronously; no new failure-mode class.
- **Separate call is load-bearing** for signals (see error handling).
